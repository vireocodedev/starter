## The three sets

Three numbers that ought to be close, and are not:

| Set           | Meaning                                                             |
| ------------- | ------------------------------------------------------------------- |
| **USED**      | Distinct symbols the consuming app actually imports.                |
| **EXPORTED**  | Symbols reachable from the package's declared entry points.         |
| **REACHABLE** | Modules an arbitrary consumer can import through the `exports` map. |

REACHABLE is the set that semver is accountable for. Anything inside it is public API whether it was meant to be or not.

## Finding 1 — the wildcard problem is `starter-ui` only

`starter-ui` is the sole package declaring `"./*"` in its `exports` map, so all 183 built modules are importable and therefore public. It is also the only package built file-for-file (`tsc` + `tsc-alias`); the other six run `vite build` and emit a single bundled entry. Those six have **no per-file artefacts to deep-import even if the map allowed it**.

This materially narrows roadmap step **1.3**. The other six packages already have a deliberate boundary; the work there is confirmation and a contract test, not restructuring.

`starter-core` is the only other package with more than one entry point (`.` and `./offline`), and that split is intentional.

> **Resolved in 1.2** for `starter-ui`. The wildcard is gone and `tests/entryPoints.test.ts` fails the build if one
> reappears. The conclusion about the other six packages held up: they need confirmation and a contract test, not
> restructuring.

## Finding 2 — the deep imports are gratuitous

The app reaches past the barrel in exactly **three subpaths**, across **18 files**, for **six symbols**:

| Subpath                         | Symbols                                          | Files |
| ------------------------------- | ------------------------------------------------ | ----- |
| `starter-ui/utils/apiutils`     | `endpoint`, `PageableParams`, `PageableResponse` | 14    |
| `starter-ui/utils/zodutils`     | `zodParse`                                       | 8     |
| `starter-ui/utils/countryutils` | `CountryCode`, `getCountryName`                  | 2     |

**All six symbols are already exported from the root barrel.** Nothing is being reached that the public entry point does not already offer, so removing the wildcard requires no new subpath for them — only a mechanical repoint of the import specifier. There is no API design decision hidden here.

> **Partly wrong, corrected in 1.2.** The symbol-level conclusion was right; the environment-level conclusion was
> not. This analysis asked only _which symbols_ were reachable, never _from which runtime_. Eight of these files end
> up in the SQLite Web Worker bundle, and the root barrel cannot be imported there: it pulls in React, MUI and
> DOM-dependent providers, which fail on load in a worker that has no `document`. The wildcard was load-bearing for
> that case, not merely convenient.
>
> So a repoint to `.` would have broken the worker. Step 1.2 added a curated **`./api`** entry point instead —
> framework-free by construction, with `tests/entryPoints.test.ts` failing the build if React, MUI or a DOM renderer
> ever enters its runtime graph, and its third-party surface frozen to `axios` and `zod`.
>
> A second entry point, **`./country`**, was added for the two country consumers. It is deliberately **not**
> worker-safe: `RGO_COUNTRY_CODES` is derived from `Object.keys(CFIFlags)` and `CountryCode` from
> `country-flag-icons/react`, so importing it evaluates React components. It exists only to spare the API layer the
> whole component library. Making country lookups genuinely worker-safe means decoupling the code list from the flag
> components — a redesign rather than a file move, and out of scope here.
>
> **Lesson for the remaining packages.** Reachability analysis alone is not sufficient to justify collapsing an
> entry point. Ask which runtimes a consumer imports from before concluding a subpath is gratuitous.

## Finding 3 — the barrel is far wider than any consumer needs

72% of exported symbols (550 of 766) are unused by the only consumer. The ratio is worst where it matters most:

- `starter-ui` — 339 of 432 unused (78%)
- `starter-core` — 96 of 151 unused (64%)
- `starter-localization` — 40 of 48 unused (83%)
- `starter-history` — 31 of 36 unused (86%)

Read this as a **question, not a verdict**. With a single consumer, "unused" cannot distinguish deliberate library surface from accidental leakage. `starter-localization` legitimately exports per-namespace resources and types the app never names directly. That ambiguity is precisely what roadmap step **2.1** is meant to resolve, and why 1.2 should not be driven by usage counts alone.

`starter-infrastructure` is the counter-example worth noting: 20 of 26 exports used. It is the one package whose surface is already sized to its purpose.

`components` subdivides into `data-display` (22), `inputs` (20), `layout` (8), `feedback` (6), `navigation`, `utility`, plus 10 loose modules sitting directly under `components/` rather than in a category.

Two observations for 1.2:

- The directory layout is a reasonable first draft of a subpath set, but `table` existing alongside `components/data-display` (which holds `RgoTable`) means the physical layout already disagrees with itself. Subpaths should be decided from intent, not mirrored from directories.
- The 10 uncategorised modules directly under `components/` have no natural home in a directory-derived scheme.

## Caveats

- USED reflects **one** consumer. It is evidence of what is load-bearing today, not of what the library is for.
- EXPORTED follows `export *` chains through source, so it counts what the barrel genuinely re-exports rather than what the barrel file lists.
- REACHABLE counts built `.js` modules. Type-only artefacts are additionally reachable in packages whose builds emit per-file declarations (`starter-core` emits 67 `.d.ts`, `starter-queryengine` 7), but without a matching `exports` entry a consumer cannot import them.
